# 议价状态一致性修复方案

日期：2026-09-18

## 问题

6020 商品已经接受顾客的 378 元报价后，顾客继续询问“怎么拍下”，程序错误地回复“378 不行，388 可以”。

根因不是模型自由发挥，而是本地确定性议价状态机只允许“可以的话我就拍”等条件式表达继承已接受价格。“怎么拍下”虽然被识别为订单相关表达，却落入“此前报价未接受”的分支，并回退到首次还价 388 元。模型和本地回复校验器随后都服从了这份错误结论。

此外，议价状态原先只存在于 `CustomerServiceWorker` 内存中。停止接待、重新启动 Worker 或重启应用后，已接受价格、上次还价和重复报价次数都会丢失。

## 修复设计

1. 单独识别“怎么拍下、怎么下单、在哪里拍”等购买操作提问。
2. 如果上一轮已经接受价格，这类提问继续使用已接受价格，不回退到首次还价。
3. 购买操作提问不视为顾客已经拍下，因此不生成订单改价任务。
4. 新增 `cs_negotiation_states` 表，按会话保存：
   - 商品键；
   - 基础价或蓝牙价版本；
   - 数量；
   - 最近顾客报价；
   - 最近还价；
   - 已接受价格；
   - 当前议价结果；
   - 重复报价次数；
   - 更新时间。
5. Worker 首次处理某会话时从 SQLite 恢复状态；生成新议价结论后同时更新内存和 SQLite。
6. 基础价与蓝牙价版本不一致时不复用旧状态，避免取消或选择蓝牙后沿用错误价格。
7. 持久化状态沿用 15 天审计保留期，自动清理过期记录。

## 验收场景

- `378 可以吗 → 怎么拍下`：两轮都保持接受 378，第二轮不生成改价任务。
- `378 可以吗 → 怎么拍下 → 你上面不是说 378 → 怎么拍下`：不会再回退到 388。
- Worker 重建或程序重启后询问“怎么拍下”：从 SQLite 恢复已接受价格。
- 基础价和蓝牙价版本发生变化：不复用另一价格版本的议价状态。
- 全量单元测试、Ruff 和编译检查通过。
