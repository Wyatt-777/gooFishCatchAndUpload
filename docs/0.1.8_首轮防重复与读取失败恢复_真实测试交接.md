# 0.1.8 首轮防重复、订单状态与读取失败恢复

实施日期：2026-10-05。已备份 0.1.7 源码、运行数据库和安装程序到 `output/backups/before-welcome-order-guard-20261005-204439/`。

## 已实施内容

1. 未指定型号的普通问价不再无条件调用首次固定话术。首次资格开放时允许一次；已接待顾客后续问价按已匹配商品报价，型号不明确时询问型号。主动索要价格表属于独立用途，可正常回复。
2. 待付款、付款、退款等订单证据先进入独立状态存储。订单卡的按钮、昵称和价格提示不作为问价文本；已拍下时取消首次话术、重新拍单引导和未下单追问。
3. 草稿生成、发送前重读、提交按钮点击前均有首轮/订单检查。旧草稿、编辑草稿、恢复任务也受限制；顾客主动请求目录必须来自实际触发消息，而不是模型自报意图。
4. 增加独立 SQLite 表：`cs_contact_guards`、`cs_contact_bindings`、`cs_order_observations`、`cs_contact_templates`。首次资格与订单状态不受15天消息和90天质检清理影响。升级从既有首次状态、发送、商家消息与订单档案补齐状态，不清空顾客。
5. 有可信商家账号、买家 ID 时进行账号内身份绑定；缺少这些字段时保留稳定平台会话身份。弱列表哈希仍禁止自动发送，不按昵称、头像合并顾客。身份冲突关闭首轮资格；发送前出现顾客或商家 ID 变化时不发送。
6. 首次发送预留采用数据库原子事务。提交结果不确定时保留资格关闭/预留状态；只在确认未执行提交时释放。模板更改记录历史版本，不重置顾客首轮资格。
7. 型号解析共享一个规则，支持全角分隔符、斜杠及单位写法。金额、日期不解释成型号。功率、运费、容量等问题不简单按“多少”解释成商品问价。
8. 消息角色优先读取明确属性和作者 DOM 结构，再使用几何位置。只使用消息专属 ID 字段，避免组件通用 `id`。无可靠 ID 时保留弱证据标记。自身回显仅凭已核验平台消息 ID 与内容双重证据纠正；不同消息 ID 的顾客复制内容仍作为顾客消息保留。
9. 已结束任务释放活跃会话占位。仅生成前、尚未提交的读取失败可按2秒、5秒间隔重读，最多三次；失败后转交该会话人工，其他会话继续。已提交或结果不确定的发送不采用此生成重读机制。

## 此次新截图问题的分析

截图箭头处为“生成前无法重新读取会话”，属于生成前重新打开/读取会话失败；不是发送后核验失败。

用户指定的 `客服对话质检包-20261005-174217.zip` 中共57条此类失败记录，统计范围包含历史版本。最新一条发生在17:33:46（17:33:33创建任务）。该会话随后在17:34:02、17:35:06、17:35:35仍有已核验的应用发送，所以不能据此认定整个客服线程已经停止。

旧代码的恢复缺口已确认：失败任务仍留在 `_job_by_conversation`，下次相同消息批次会被“已有任务”跳过，而待处理筛选不包括失败任务。新顾客消息改变批次后，可能重新生成，因此表现为某条消息不再回复，而新消息可能又恢复。

本次已修补占位释放和有限重读，并保存原始异常类型、错误摘要和会话查找诊断。旧包只保存了笼统的失败描述，不能确定最初读取失败究竟是页面重绘、目标会话查找超时、连接问题还是其它读取错误。

## 关于接近400次轮询后不录入新消息

源码没有400次轮询的停止条件。本包 `fault_log.txt` 不含完整 `poll_complete` 轨迹，最新运行109在17:42:05开始，导出时只记录到17:42:19。无法把“接近400次”与某次停滞可靠对应，也不能保证修补某条失败任务就解决了所有长期运行问题。

0.1.8每10次轮询以及停止时增加 `poll_progress` 质检事件，记录候选、新消息、待生成、跳过原因、模型等待数、恢复状态、页面最后正常时间和轮询耗时。生成中/等待模型的任务也计入待生成，不再只统计防抖任务。

| 新版证据 | 优先排查方向 |
| --- | --- |
| 轮询持续，主要跳过已有任务/读取重试 | 任务占位、恢复路径、单会话读取 |
| 候选长时间为0，但平台有新消息 | 会话列表采集、页面选择与虚拟列表 |
| 候选存在，主要是已转人工 | 人工锁是否符合当前会话状态 |
| 模型等待长期存在 | API请求或模型任务等待 |
| 浏览器恢复标记存在 | 连接、客服页面失效与重连 |
| 心跳和轮询事件一起中断 | 线程阻塞、持久化或进程问题 |

这些是诊断方向，不是对400次那次故障已经确认的根因。
