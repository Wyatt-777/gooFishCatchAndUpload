# 客服接待稳定性压测与故障排查方案

## 当前实施结果（2026-09-25）

- 已加入无顾客原文的轮询心跳、阶段切换、耗时、候选数、待处理数、最老待处理时长、跳过原因和任务状态转换日志；运行界面每秒显示当前阶段、持续时间和上次健康时间。
- 已将日志限制为 5 MB × 4 个轮换文件，页面诊断目录改到 `%LOCALAPPDATA%\XianyuAssistant\diagnostics\customer_service`。
- 已将发送点击后回读未确认、或发送中抛出不确定异常的任务转成人工核对，避免下一轮自动重发；重启恢复时的 `sending` 任务原有逻辑也转人工。
- 新增只读汇总工具 `scripts/customer_service_diagnostic_report.py`，只输出运行状态、故障分类、任务状态计数与心跳统计；`scripts/monitor_customer_service.ps1` 可采样进程 CPU、内存、句柄、线程和磁盘空间。
- 离线 100 会话突发、慢模型 20 秒心跳和回读未确认不重发测试通过；全套 260 项测试通过。
- 尚未完成浏览器虚拟列表覆盖率实测、真实平台 CDP 故障注入和 2／24／72 小时长跑。这些需要测试账号、可控浏览器页面和持续运行时间，当前不能据此宣称已定位真实环境的历史故障。

运行中的旧版 EXE 不会自动载入这次源代码修改。测试新版前，应关闭旧版并启动独立构建的新版；不要同时让两个实例接管同一个客服账号。

本机只读汇总：`.venv\Scripts\python.exe scripts\customer_service_diagnostic_report.py`。两小时资源采样：`powershell -NoProfile -ExecutionPolicy Bypass -File scripts\monitor_customer_service.ps1 -DurationSeconds 7200`。汇总不含聊天正文；页面截图诊断仍可能含可见聊天内容，仅保存在本机，不应直接外传。

## 目标

找出“应用还在但不回复”“接待状态变成已暂停”“应用进程退出或卡死”三种现象的具体原因。压测必须同时验证及时回复、不会重复发送、不会发到错误会话，以及故障能被明确记录和展示。所有模拟发送先在假页面或测试账号进行，不使用真实顾客会话做故障注入。

## 现有证据与待核实风险

本机 `%LOCALAPPDATA%\XianyuAssistant\xianyu_assistant.db` 的 `cs_run_sessions` 当前为 0 条；近 14 天 Windows Application 日志中也没有检索到带 `XianyuAssistant` 名称的应用崩溃事件。这只能说明本机没有可用于还原那次实测故障的运行记录，不能说明真实环境没有故障。要分析已发生的故障，应取发生故障的那台电脑上的运行状态、日志和脱敏诊断。

| 现象或风险 | 代码依据 | 压测重点 |
| --- | --- | --- |
| 页面登录失效、验证码、风控立即全局暂停；页面结构或列表读取连续 3 次失败也暂停 | `CustomerServiceWorker.run_once`、`check_page_health` | 短暂空列表、页面加载慢、CDP 断开与真正风险控制要能区分 |
| DeepSeek 连续 3 个任务失败会暂停；发送连续 3 次失败会暂停 | `_record_model_failure`、`_record_send_failure` | 429、5xx、超时、无效 JSON、数字校验失败和回读延迟分别归因 |
| 顺序处理可能造成“进程活着但长时间无回复” | `_process_due_jobs` 顺序执行；客户端 20 秒超时、每请求最多 2 次，Worker 最多 2 次回复尝试，另有语义分析调用 | 单任务最坏约 80 秒，含语义分析约 120 秒；10 个慢任务可阻塞后续会话约 20 分钟。需实测并限制队列老化 |
| 虚拟会话列表只遍历当前挂载的行；非未读、无变更标记且非当前会话的行会被过滤 | `PlaywrightXianyuChatAdapter.list_changed_conversations` | 大量会话、列表滚动、未读标记被平台清除时是否漏扫 |
| 某会话已转人工或平台显示发货，后续消息会被跳过 | `has_open_handoff`、`_intercept_post_fulfillment` | 区分全局暂停和单会话人工接管，并核对 UI 提示 |
| 人工模式草稿等待确认、旧消息指纹已处理、发送前出现新消息时均不会自动回复 | `_register_snapshot`、`_send_after_reread` | 明确记录“预期跳过”的原因，避免误判为卡死 |
| 发送点击后最多约 2.5 秒回读；本次已改为未确认即转人工，但实际页面晚回显仍需实测 | `verify_outgoing`、`_send_after_reread`、`_register_snapshot` | 故意延迟页面回显 3–10 秒，验证人工核对提示及零重复发送 |
| 浏览器连接和客服专用页没有自动重连流程 | `BrowserManager.connect`、`CustomerServiceWorker.start` | 浏览器重启、CDP 断开、标签页关闭后的恢复路径 |
| 线程异常会使本轮退出；销售追问读取数据库等路径没有统一的轮询外层故障隔离 | `CustomerServiceRunThread.run`、`_process_due_sales_follow_ups` | SQLite 锁、磁盘只读、数据库异常是否变成全局异常退出 |
| 诊断截图已改写本机应用数据目录，写入失败仍会被吞掉 | `ChatAdapterDiagnostics` | 模拟目录不可写并验证日志或 UI 可见性 |
| UI 已显示轮询与阶段心跳，但浏览器、模型和数据库内部耗时仍缺细分 | `CustomerServiceRunThread.run`、`CustomerServicePanel` | 区分模型阻塞、浏览器阻塞、消息漏扫和进程退出 |

上述是代码路径及潜在风险，不等于已确认的实测根因。尤其“发送回读慢可能重发”需要故障注入证实。

## 压测前先补的观测点

用本地结构化事件记录 `run_id`、匿名会话标识、任务 ID、阶段、开始与结束时间、耗时、结果码；不要记录顾客原文、截图内容、API Key 或完整商品隐私数据。至少包含：

- 每轮心跳：轮询开始／结束、页面健康状态、候选会话数、已选会话数、待生成队列数、最老任务等待时间；
- 每个会话的跳过原因：无新顾客消息、已处理指纹、等待人工审核、开放转人工、发货锁、会话身份变化、旧草稿废弃；
- 模型阶段：语义分析与回复生成分别计时，记录尝试次数、超时／HTTP 分类、解析和本地校验结果；
- 发送阶段：预留、填入、点击、回读确认、持久化各阶段分别计时，记录“不确定是否发送”状态；
- 系统状态：应用和浏览器进程是否存活、CPU、内存、句柄数、线程数、数据库大小及磁盘剩余空间；
- UI：显示最后成功轮询时间、当前处理阶段和持续时间、全局暂停原因、各会话人工接管原因。

心跳超时需按阶段判断：模型调用允许较长的有限时间，但同一阶段超过其配置上限、轮询长时间无结束事件，或进程已退出，都应显示明确故障。诊断文件应写到本地应用数据目录，而非安装目录。

## 分层测试

### 1. 离线确定性故障注入

使用假时钟、假页面、假模型和临时 SQLite，不连接真实闲鱼。覆盖以下矩阵，每例同时断言任务状态、全局状态、下一轮能否继续、发送次数和审计记录。

| 类别 | 注入条件 | 必须观察的结果 |
| --- | --- | --- |
| 消息洪峰 | 1、10、50、100 个会话；每会话 1–20 条连续消息；顾客不断插话 | 不漏消息、不饿死后排会话；旧草稿废弃，不发送旧回复 |
| 模型故障 | 1–3 次超时、429、5xx、无效 JSON、空响应、错误数字；多个慢任务排队 | 失败计数准确；全局暂停阈值准确；正常会话等待时间可量化 |
| 浏览器故障 | 空列表 1–3 轮、列表虚拟滚动、选择会话延迟、标签页关闭、CDP 断开、登录跳转、验证码 | 暂态可恢复；需要人工介入的状态明确暂停且不误发 |
| 发送不确定 | 点击未生效、点击成功但页面 3/5/10 秒后才显示、回读抛错、进程在点击前后被终止 | 绝不重复发送；不确定结果转人工核对；其他会话继续 |
| 持久化故障 | SQLite 锁、只读、磁盘满、事务提交失败、重启恢复中断任务 | 不丢状态、不把已发送变为可重发；错误分类可见 |
| 人工与自动交错 | 人工在浏览器发消息、审核草稿时顾客再发、人工接管与解除、切换接待模式 | 自动任务及时废弃；转人工后不继续自动回复 |
| 媒体与订单 | 图片读取失败、语音转写失败、发货／签收标记、改价失败、销售追问到期 | 只影响相应会话或按已定义安全阈值暂停；不出现错误订单操作 |

### 2. 浏览器仿真压测

用可控 HTML/DOM 和 CDP 浏览器模拟闲鱼会话列表、消息流及页面异步更新。重点测试虚拟列表滚动、未读标记瞬时消失、消息 ID 变化、消息晚渲染、页面重绘和选择会话后短暂读到旧内容。记录实际扫描覆盖率与错误会话发送数。

### 3. 长时间稳定性

先做 2 小时高频混合负载，再做至少 24 小时持续负载，最后做 72 小时低频真实节奏运行。每 30 分钟注入一次可恢复故障，定期重启浏览器和应用，覆盖跨重启的草稿、议价、发送预留与人工接管恢复。记录每小时吞吐、回复延迟、队列最大年龄、资源曲线和所有暂停事件。

### 4. 真实环境灰度

先在人工审核模式观察草稿与日志，再用测试账号／可控会话验证全自动模式；最后对少量真实会话分时段开放。下单引导开关保持默认关闭，单独比较开关前后的回复延迟和异常率。故障注入不对真实顾客进行，真实环境只观察自然故障并及时人工接管。

## 判定标准

1. **安全硬门槛**：错误会话发送、已废弃草稿发送、未经确认的重复发送、发货后自动回复均为 0。
2. **可诊断性**：每个“暂停／不回复”样本必须归入全局暂停、单会话跳过、队列阻塞、模型／浏览器／数据库失败、进程崩溃之一，并能定位到阶段与时间；未知原因计数为 0。
3. **队列与延迟**：记录从顾客消息到草稿／发送的 p50、p95、p99，以及最老任务等待时间。先测正常模型延迟基线，再设不同并发档位的上限；不能只检查平均值。
4. **恢复**：可恢复故障解除后无需重复发送即可继续处理；需要人工处理的故障在 UI 明示原因和操作，不以“运行中”掩盖停滞。
5. **资源**：24 小时内内存、句柄、线程和数据库大小无持续单调增长；超出基线 25% 的持续增长必须解释并复测。

## 实施顺序与交付物

1. 先补观测点和只读诊断导出，建立单次故障的时间线。
2. 优先验证“慢模型串行阻塞”“发送回读慢可能重发”“虚拟列表漏扫”三项高风险假设；确认后先修复，再进入长跑。
3. 完成上述故障注入矩阵、浏览器仿真和 24/72 小时运行。
4. 每次失败保留匿名事件链、进程资源曲线、必要的本地脱敏页面证据，以及对应的最小复现测试。
5. 形成一份按发生频率与影响排序的根因报告，列明已确认原因、排除的原因、尚需真实环境验证的原因和修复后的复测结果。
