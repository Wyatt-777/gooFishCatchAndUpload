# 发货后转人工实施说明

首次实施：2026-09-21；触发条件更新：2026-09-22
版本：0.1.4

## 行为

- 仅将闲鱼聊天时间线中平台生成的“你已发货”系统事件作为新人工锁的确定证据。
- “已付款”“待发货”“等待买家收货”不会触发本规则；“订单已签收”仍会被识别，但不再新建人工锁。
- 已发货订单会话在模型调用、自动改价、人工草稿发送和销售追问前均会被拦截。
- 顾客在发货后发送新消息时，应用创建转人工通知，不发送任何自动回复。
- 发货后人工锁按会话/订单保存，不会仅凭顾客昵称影响其他商品会话。
- 升级前已经保存的已签收人工锁继续有效，不会因规则升级恢复自动回复。

## 数据

- `cs_conversation_fulfillment` 长期保存会话履约状态、平台证据、发货时间和自动接待锁。
- `cs_customers.fulfillment_status` 与 `shipped_at` 保存顾客主档的发货事实摘要。
- `cs_customer_state_events` 记录 `platform_order_shipped` 和人工恢复事件。
- `cs_handoff_events` 为兼容旧数据库继续使用 `post_delivery` 内部类型；关闭本次通知不会解除人工锁。

## 人工操作

- “已处理本次消息（保持人工）”：只关闭当前提醒，已发货会话继续由人工接待。
- “恢复该会话自动接待”：明确解除该会话的发货后人工锁；相同平台发货事件再次被读取时不会重新上锁。

## 安全边界

- 平台系统事件不会混入顾客/商家聊天上下文，也不会发送给模型。
- 发送前重新读取页面；如果生成草稿期间出现“你已发货”，旧草稿立即作废并转人工。
- 页面或数据库中的发货状态读取异常时采用失败关闭策略，不冒险自动回复。
